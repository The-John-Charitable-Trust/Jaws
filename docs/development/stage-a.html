Stage A: Discover and Reconcile Azure State

JAWS development tutorial · Status: Stage A discovery accepted. This tutorial documents the implemented installer, not a proposal to create resources.

1. Purpose and architecture

Stage A establishes a state-first, read-only discovery process. The operator-maintained installation state file is the desired-state authority; the installer scans Azure resources visible to the authenticated identity, compares live resources against the state, and writes evidence reports. Discovery does not create, delete, or reconfigure Azure resources and does not rewrite the authoritative state.

For the current development environment, the target is the East US JAWS environment in rg-aiops-lab. Stage A discovers the Foundry account, Foundry project, model deployment, and Key Vault. Legacy or unrelated infrastructure is not an installation target.

2. Prerequisites

Use a Windows workstation with VS Code, PowerShell 7, Git, Azure CLI and Pester 5.9.1. Azure sign-in must have read access to the authorized subscriptions and the target resources. Repository branch: codex/0.2-add-mcp-server.

cd "C:\Users\CecilJohn\Documents\jaws\JawsOSS"
git status -sb
git pull --ff-only origin codex/0.2-add-mcp-server
az account show --output table
Import-Module Pester -RequiredVersion 5.9.1 -Force

Do not force a pull over uncommitted changes. Resolve Git changes first.

3. Read the authoritative state

code .\installer\config\jaws-installation-state.dev.json

Verify Platform=JAWS, EnvironmentName=dev, the authorized subscription, rg-aiops-lab, and four expected resource entries. The state JSON is the gold copy; generated evidence belongs under installer/.local/. Never replace the state file with a discovery report.

4. Run Stage A discovery

.\installer\Install-Jaws.ps1 -Mode Discover -EnvironmentName dev -NonInteractive

The installer reads the operator-maintained state, enumerates visible enabled subscriptions, checks the authorized resource group, scans the tenant, discovers expected resources, and reconciles them to the state. A subscription or permission mismatch is a stop condition, not permission to select another environment silently.

Inspect generated reports in installer/.local/, especially jaws-tenant-scan.dev.generated.json, the state comparison and resource discovery output. File creation is local only.

5. Execute the acceptance tests

Invoke-Pester .\tests\installer\ -Output Detailed

The original Stage A acceptance baseline was 21 passing tests. The installer suite subsequently expanded as Stage B was built; the total displayed today is therefore expected to exceed 21. Acceptance requires zero failures, completed tenant scan, consistent targeted resource reconciliation and no Azure infrastructure writes.

Compare the state with discovered Foundry, project, model deployment, and Key Vault identities. Record missing resources or configuration drift explicitly; never count absence as success.

6. Safety and troubleshooting

SituationRequired response
Azure authentication missingSign in using the organization's authorized account; do not change subscription implicitly.
Tenant scan incompleteStop and inspect the generated scan; do not report complete discovery.
State differs from AzurePreserve the state file; record the discrepancy for reviewed planning.
Git contains local editsPreserve edits before updating the branch; avoid forced resets.
