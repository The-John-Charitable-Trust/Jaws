Stage B: Install and Accept the JAWS Supervisor

JAWS development tutorial · Supervisor installation milestone: deployed, reconciled, and authenticated conversation verified on October 13, 2026. Full Stage B multi-agent platform acceptance remains pending.

This tutorial documents the successfully exercised installer-managed workflow and the checks that separate Azure resource creation from actual runtime acceptance. Repeat executions must discover existing resources, not create duplicates.

1. Architecture and boundaries

JAWS uses a .NET 10 Supervisor hosted as a Microsoft Foundry agent. The Linux/amd64 container is published to a dedicated Azure Container Registry. The Foundry project's managed identity has registry-scoped image-pull permission. The Supervisor exposes Responses protocol 2.0.0. No specialist worker, Azure MCP, Datadog MCP, remediation or Teams integration was validated as part of this milestone.

2. Build and publish the Supervisor

After synchronizing the branch, install required .NET SDK, PowerShell 7, Azure CLI, Docker Desktop/WSL2 and Pester. Validate the local package before any cloud publication.

.\installer\Install-Jaws.ps1 -Mode Package
.\installer\Install-Jaws.ps1 -Mode Package -BuildContainer
.\installer\Install-JawsRegistry.ps1 -Mode Plan
.\installer\Publish-JawsSupervisor.ps1 -Mode Plan

The registry creation and image publication paths require explicit separately approved operations and carry cloud-cost implications. Use the matching installer plan, approved digest and billing acknowledgment exposed by the current script; never create the registry manually or publish a mutable unverified image. The development registry and its published immutable image already exist. Do not repeat a billable creation/push merely to validate the current deployment.

The accepted image is identified by its ACR hostname and immutable SHA-256 manifest digest. Evidence files are written under installer/.local/.

3. Foundry image-pull access

The project's managed identity must have AcrPull for a registry using legacy registry permissions, or the appropriate repository-reader role for ABAC mode. Only the installer may perform a separately approved assignment. Before retrying any assignment, inspect existing RBAC and reconcile its principalId, role and exact registry scope.

.\installer\Install-JawsFoundryAcrRbac.ps1 -Mode Plan

The existing JAWS development assignment has been confirmed. No further role assignment is required for Supervisor v1. A displayed principalName is not a substitute for the actual principalId.

4. Foundry Supervisor deployment

The installer uses a SHA-256-bound Plan followed by an explicitly authorized Deploy step. Deploy is a potentially billable Azure change. A successful API write must not be repeated because receipt parsing failed. After creation, reconcile the existing version.

.\installer\Deploy-JawsSupervisor.ps1 -Mode Plan
# Deploy only for a NEW approved resource/change, never as a retry for an existing v1:
# .\installer\Deploy-JawsSupervisor.ps1 -Mode Deploy -ApprovedPlanSha256 $approvedHash -AcknowledgeHostingAndInferenceCharges

Hosted-agent environment variables in the persisted version include AZURE_AI_MODEL_DEPLOYMENT_NAME=gpt-5-mini. Reserved platform-managed prefixes FOUNDRY_ and AGENT_ must not be added as user-supplied deployment environment variables. The platform supplies the required hosted runtime context.

The deployed dev agent version 1 reports active, uses 1 CPU and 2 GiB, and declares Responses protocol 2.0.0. The creation response parser supports both version-record and summary-style shapes. JSON submission uses safe file-based transport for Windows PowerShell.

5. Verify and reconcile existing Azure state

Reconciliation retrieves the specific /agents/jaws-supervisor-dev/versions/1 record, not the incomplete agent summary. It compares name, version, status, hosting kind, image digest, model, CPU, memory, protocol and forbidden reserved environment-variable prefixes. Mismatches produce a field-level report; they do not authorize another Azure deployment.

Invoke-Pester .\tests\installer\ -Output Detailed
.\installer\Test-JawsSupervisorDeployment.ps1

On first recovery only, the installer may generate the local deployment receipt using the current matching plan hash:

$plan = Get-Content ".\installer\.local\jaws-foundry-supervisor-plan.dev.generated.json" -Raw | ConvertFrom-Json
.\installer\Recover-JawsSupervisorDeployment.ps1 -ApprovedPlanSha256 $plan.PlanSha256
If JAWS-RECOVER-006 reports that the deployment receipt already exists, do not overwrite or delete it. Inspect the receipt and reconciliation report, then proceed to verification. Current environment already has a recovered receipt.

Evidence: jaws-foundry-supervisor-reconciliation.dev.generated.json and jaws-foundry-supervisor-deploy-receipt.dev.generated.json.

6. First authenticated conversation and acceptance

The runtime test uses the existing agent's Responses endpoint, checks the live version's approved configuration, and sends an explicitly acknowledged inference request. It records response ID, status, output length and latency without changing Azure infrastructure.

.\installer\Test-JawsSupervisorInvocation.ps1 -AcknowledgeInferenceCharges

This invocation can incur model inference charges. It should not be rerun needlessly after successful acceptance. The test prompt asks the agent to identify its role and avoid claiming access to tools that were not configured.

Observed result: The hosted Supervisor returned a substantive response about incident coordination and safeguards, and the installer generated jaws-supervisor-invocation-acceptance.dev.generated.json. Infrastructure status, image reconciliation, and one authenticated invocation passed. The management API's active status alone would not have met this acceptance criterion.

To inspect existing evidence without causing another inference request:

Get-Content ".\installer\.local\jaws-supervisor-invocation-acceptance.dev.generated.json" -Raw | ConvertFrom-Json | Format-List *

Keep local environment-specific receipts out of the public repository. Results should include InvocationVerified=True in the separate invocation evidence; the earlier deployment receipt may still show InvocationVerified=False as a historical point-in-time record.

7. Remaining Stage B milestones

The following capabilities are not yet accepted: Investigation and specialist agent delegation, Azure Policy and Defender MCP integration, Datadog MCP integration, isolated worker compute, durable conversation context, least-privilege security broker, human approvals for executable actions, Teams channel integration, and complete end-to-end operational verification.

Next development checkpoint: design and test Supervisor-to-Investigation delegation with authenticated, read-only evidence handling before extending access to MCP tools. Preserve the existing accepted Supervisor and its receipts.
