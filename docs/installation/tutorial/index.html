Introduction: Start with your own Azure subscription

JAWS is an Azure-hosted agentic operations platform. Its planned architecture connects Microsoft Teams to a Supervisor and specialist agents, with authorized tools, human approval and evidence-backed outcomes. This tutorial is intended for a new customer or installation engineer with no existing JAWS infrastructure.

Release-readiness notice. Engineering milestones A–C have been exercised in the original development environment. The current primary installer does not yet provide full provisioning into a new subscription: Install-Jaws.ps1 supports Discover, Plan and Package only. Do not treat DEV validation as proof that a clean customer installation works. The greenfield installer specification defines the missing capability.

Before using this tutorial

  1. Have an active Azure subscription and a Microsoft Entra account with appropriate permissions. Resource discovery typically requires scoped Reader access; provisioning generally needs Contributor or scoped equivalent, separate role-assignment privileges and applicable Foundry access.
  2. Install PowerShell 7, Git and Azure CLI. For local builds/tests, also install WSL 2, Docker Desktop (Linux containers), .NET SDK 10 and Pester 5.
  3. Read Quick Start for official download links and prerequisite verification and the complete prerequisite specification.

Clone the source

git clone --branch feature/step-c-investigation-publishing https://github.com/The-John-Charitable-Trust/Jaws.git
cd Jaws
git status

Use an appropriate reviewed release branch or tag when published. Branch above is the currently documented engineering baseline, not a permanent customer release designation.

End-State System Architecture

The reference diagram describes the intended final system independently of what has been installed. The Supervisor routes specialist work; it does not call Azure services directly. The VM Specialist owns one compute environment, while the Observability Specialist uses shared compute through a custom MCP integration boundary.

Security and execution boundaries

Operator identity, least-privilege RBAC, managed identities, project isolation and approval gates are cross-cutting requirements. The Step C prompt planner is an A2A callee, not proof of a running VM investigation workflow. Refer to the approved roadmap.

Concept of Operations

An operator requests assistance, the Supervisor delegates work to an appropriate specialist, authorized tools gather evidence, the specialist evaluates options, a person authorizes applicable changes, and the system executes, validates and reports results. When evidence is insufficient or approval is denied, the workflow must stop or return to investigation safely.

Important: The complete ConOps is a design target. Steps A–C do not constitute a working Teams incident-to-remediation workflow.

Step A: Azure Discovery and Reconciliation

Value proposition: Establish which Azure resources are visible to your identity and produce a read-only baseline before JAWS changes anything. A new, empty subscription is a valid result.

A1. Authenticate and confirm scope

az login
az account list --query "[].{Name:name,SubscriptionId:id,State:state}" --output table
az account set --subscription "<your-subscription-id>"
az account show --query "{name:name,id:id,tenantId:tenantId}" --output table

Expected result: The selected enabled subscription and tenant are displayed. No JAWS infrastructure is necessary.

A2. Inspect Azure inventory

az group list --output table
az resource list --output table

Expected result: Readable resource groups and resources appear, or an empty result for a clean subscription. Insufficient permissions produce an actionable Azure error.

A3. Reconcile only if JAWS already exists

.\installer\Install-Jaws.ps1 -Mode Discover -EnvironmentName <environment-name> -StateFile "<path-to-existing-jaws-state.json>"

Expected result: The existing installation's tenant scan and target comparison are printed. Never borrow the DEV state file for a customer subscription. For a new empty subscription, skip A3: installer v0.4.6 rejects absent state with JAWS-STATE-003. This is a product gap awaiting the greenfield installer, not a customer setup error.

A4. Review evidence and verify zero writes

For an existing JAWS deployment, examine these files under installer/.local/:

jaws-tenant-scan.<environment>.generated.json
jaws-resources.<environment>.generated.json
jaws-state-comparison.<environment>.generated.json

Expected result: Azure writes: 0, preserved gold-copy installation state, and resource comparison results. For a clean subscription, document the Azure CLI inventory as the manual baseline until the greenfield installer generates receipts.

Expected results for completion

Existing JAWS: Correct identity and subscription, complete readable tenant scan, expected resources compared, three reports saved, zero Azure writes. New customer: Identity, subscription and empty/observed inventory recorded, zero Azure changes. Greenfield automated installation remains pending.

Acceptance criteria (A-01 through A-06)

  1. A-01: Authentication and intended subscription/tenant confirmed.
  2. A-02: Readable scope inventoried and errors visible; empty inventory is valid.
  3. A-03: Existing-state reconciliation only when an authentic installation state exists.
  4. A-04: No Azure writes and no modification of authoritative state.
  5. A-05: Baseline and applicable JAWS-generated reports retained.
  6. A-06: Automated greenfield discovery/state initialization is **not accepted** until implemented and tested.

Source and tests: Install-Jaws.ps1 · Detailed Step A tutorial · Microsoft references & acceptance.

Step B: Foundry Foundation and Packaging

Value proposition: Establish a managed Foundry project, model and secure hosted-agent packaging for repeatable deployment. Existing DEV resources are implemented and used; this is not evidence of an accepted installation into an empty customer subscription.

B1. Review an offline deployment plan

.\installer\Install-Jaws.ps1 -Mode Plan

Expected result: An offline plan produced using the repository's example blueprint, with no Azure writes. Inspect the plan and replace customer-specific inputs through supported mechanisms as greenfield install development matures; do not assume the example is a complete install.

B2. Inspect package readiness

.\installer\Install-Jaws.ps1 -Mode Package

Expected result: A local package plan, without Azure deployment. Container building is an explicitly separate development operation requiring Docker and .NET prerequisites:

.\installer\Install-Jaws.ps1 -Mode Package -BuildContainer

Expected result: A local image-build attempt using the current packaging module; success depends on local toolchain and source readiness. It does not push or deploy to Foundry.

Expected results for completion

Offline plan and local packaging validation, with no cloud writes; existing DEV Foundry resources can be validated using documented environment-specific gates. A fresh-install success cannot be claimed before authorized greenfield deployment and its acceptance tests pass.

Acceptance criteria

  • Plan and package modes must remain nonmutating.
  • Packaging must target the supported hosted container platform/architecture and preserve image provenance.
  • Foundry, model, ACR and identity readiness must be verified before deployment.
  • New-subscription provisioning, RBAC and functional acceptance remain release gates.

Sources: Foundry hosted agent deployment · Code references and acceptance.

Step C: Supervisor-to-Investigation Planner Delegation

Value proposition: Demonstrate authenticated and auditable A2A planning, where hosted Supervisor v5 delegates to the prompt-based Investigation Planner and receives a read-only investigation plan.

These commands are for an **existing, authorized JAWS development deployment** with the recorded Foundry resources, toolbox and roles. They cannot create a new subscription installation. The hosted Investigation agent is retained but was not the executed target of successful Step C A2A delegation.

C1. Read-only environment validation

.\installer\Install-JawsThroughStepC.ps1 -Mode Validate

Expected result: VALIDATED with all non-billable gates passing; no Azure configuration writes. Receipt: installer/.local/jaws-step-c-install.dev.generated.json.

C2. Functional acceptance (billable inference)

.\installer\Install-JawsThroughStepC.ps1 -Mode Validate -AcknowledgeInferenceCharges

Expected result: CLOSED, Acceptance Passed, and TASK_STATE_COMPLETED. Report: installer/.local/jaws-step-c-final-acceptance.dev.generated.json. The acceptance call may use store=false; preserve its local receipt.

C3. Repair only a documented configuration gap

.\installer\Install-JawsThroughStepC.ps1 -Mode Install -AcknowledgeStepCInstall

Expected result: When separately approved and a repairable gate is blocked, the installer applies only the allowed correction, then rechecks it. An already-correct project should require no Azure mutation. See the runbook before running this action.

Expected results for completion

Active Supervisor v5 routed; planner v1 and toolbox v2 verified; authorized A2A completion returned; identity/role boundary verified; Supervisor v1 preserved; acceptance receipt saved. This is a DEV milestone acceptance, not a customer greenfield release.

Acceptance criteria

  • Supervisor image and version detail match approved active, non-draft deployment.
  • A2A connection targets the prompt planner using approved identity mechanism; toolbox shape matches the verified implementation.
  • Read-only VM investigation plan returns as a completed A2A task through the Supervisor.
  • Failure paths do not create unintended releases or privilege assignments.
  • Installer test regressions pass and billable inference requires explicit acknowledgment.

Sources: Operator runbook · Delegation and technical boundaries · Microsoft references and acceptance · accepted Step C PR.

Release, Security and Test Boundaries

Installation must require explicit approval for Azure writes and billable resources. Never place credentials, tokens, secrets or sensitive customer installation state in GitHub. Preserve existing DEV releases and privileges. Record real test results; unexecuted tests must be marked pending or blocked, never passed.
