### 4. Investigation: why 77 tests failed on Windows

1. **Symptom:** almost every failure was `InvalidOperation: You cannot call a method on a null-valued expression`, and after the run `git` was no longer on PATH.
2. **Narrowed down:** ran only `StepA.Tests.ps1` with `-Output Detailed`. The real error was in `BeforeAll`:
   ```
   CommandNotFoundException: The term 'chmod' is not recognized ...
   at <ScriptBlock>, tests/installer/StepA.Tests.ps1:34
   ```
3. **Root cause:** every installer test fakes Azure CLI with a file called `az` that is a `#!/bin/bash` script running `exec python3 "$0.py"`, made executable with `chmod +x`. Some tests set `PATH` to `<stub>:/usr/bin`. All of that is Linux-only. The commit history shows the tests were written by "Cursor Agent", which runs on Linux.
4. **Conclusion:** not a machine problem. The suite only runs on Linux. The docx's "21 Pester tests passed" baseline is from the old repo `cezjah/Jaws` on branch `codex/0.2-add-mcp-server`. `main` now has 81 tests.

### 5. Investigation: running the tests in Linux (Docker)

1. **First container run:** 40 passed / 41 failed. Every failure said:
   ```
   Program 'az' failed to run: An error occurred trying to start process '/tmp/jaws-...-stub-.../az' ... No such file or directory
   ```
   The file existed, so "No such file or directory" pointed at the **interpreter** named in the shebang.
2. **Root cause:** `git config core.autocrlf` = `true`, and `StepA.Tests.ps1` had 84 CR bytes. The here-string that writes the stub carries CRLF, so the shebang becomes `#!/bin/bash\r`, and Linux looks for a program literally called `bash\r`.
3. **Fix (environment only, repo untouched):** the container copies the read-only mounted repo to `/work` and strips `\r` from `*.ps1 *.psm1 *.json *.py` before running Pester.
4. **Second run:** 80 passed / 1 failed.

### 7. Finding: the same bug is live in 6 production calls

Checked each command with `az <command> --help` on Azure CLI 2.91.0:

| Command | `--yes` supported |
|---|---|
| `cognitiveservices account delete` | ❌ |
| `cognitiveservices account project delete` | ❌ |
| `cognitiveservices account deployment delete` | ❌ |
| `cognitiveservices account create` | ✅ |
| `containerapp delete`, `containerapp env delete`, `group delete` | ✅ |

```
$ az cognitiveservices account delete -n x -g y --yes
ERROR: unrecognized arguments: --yes
```

`grep` found `--yes` on unsupported commands at:
- `installer/modules/Uninstall.psm1` lines 306, 379 (deployment delete), 320 (project delete), 326, 383 (account delete). These came in with Cursor PRs #57/#58, after #39.
- `installer/modules/StepBInstall.psm1:749` (deployment delete, only when `-QuotaMode Dynamic` replaces a GlobalStandard deployment)

**Impact:** a real `Uninstall-Jaws.ps1` would stop at `JAWS-UNINSTALL-010` on the first deployment delete. The `-AllowMissing` filter (`MISSING|ResourceNotFound|...|Not Found`) doesn't match "unrecognized arguments", so it throws, and **billable resources keep running**. The tests never caught it because the Uninstall and Step B stubs accept any flag.

Creates the resource group, Foundry account and project, `gpt-5-mini` deployment, Key Vault, Basic ACR, AcrPull, and Supervisor v1. Pass: `STEP-B ACCEPTANCE PASS`. Needs Contributor plus role-assignment rights.
- **C, Delegation:** Supervisor → RemoteA2A → Investigation prompt planner via a toolbox. Adds one Foundry Agent Consumer role and a new Supervisor version (v1 untouched). Pass: `CLOSED`, `TOOL_INVOKED_SUCCEEDED`, `TASK_STATE_COMPLETED`.

Pass: `STEP-D ACCEPTANCE PASS`, `Next step: Step E Validate`. Don't run `Install-JawsFoundryPrivateNetwork.ps1` before Step C passes, because it deletes the Foundry account.
