1. Prepare for your first JAWS installation

This guide is for an organization installing JAWS in its own Azure subscription. You do not need an existing JAWS installation, a special development subscription, or a pre-created JAWS resource group. The installer is intended to collect your Azure subscription and deployment choices, assess prerequisites, present a deployment plan, obtain authorization and provision JAWS. Release status: the complete first-time provisioning workflow is not yet implemented. The commands later on this page are limited to currently supported discovery, planning, packaging or existing-environment validation; they are not substitutes for a new installation.

For detailed workstation configuration see System Prerequisites. For design and acceptance requirements see Implementation Roadmap and Microsoft References & Acceptance Criteria.

Hardware and operating system

  • Windows 11 workstation with hardware virtualization enabled. Development workstation recommendation: 32 GB RAM / 1 TB SSD, especially for Docker Desktop, WSL 2 and .NET builds. The repository does not establish an absolute minimum RAM/disk requirement.
  • Internet access to GitHub, Microsoft package downloads, Azure management endpoints, Microsoft Foundry and the authorized container registry.

Azure subscription, permissions, and readiness

Bring your own active Azure subscription. JAWS must not require a pre-existing JAWS deployment, a development subscription, or a fixed subscription ID. The intended installer workflow must ask the operator to select an accessible subscription and choose or create a target resource group. Current release limitation: the available installer does not yet provision a complete new installation; implementing this is a release-blocking requirement for customer installation readiness.

PowerShell policy and source trust

Review Get-ExecutionPolicy -List before running downloaded PowerShell scripts. Respect MachinePolicy/UserPolicy; do not permanently bypass them. See Microsoft execution-policy guidance. Docker uses WSL 2 Linux containers, and hosted images target linux/amd64; Docker is not necessary for read-only inventory checks.

Get JAWS source and select the subscription

git clone --branch feature/step-c-investigation-publishing https://github.com/The-John-Charitable-Trust/Jaws.git
cd Jaws
az login
az account list --query "[].{Name:name,SubscriptionId:id,State:state}" --output table
# Choose your target Azure subscription:
az account set --subscription <your-subscription-id>
az account show --query "{name:name,id:id,tenantId:tenantId}" --output table
Get-ExecutionPolicy -List

Important: az account set selects a subscription for the Azure CLI. Step A discovery also takes -SubscriptionId and does not load the development state file. Step C validation still targets the existing development project. Do not pass installer/config/jaws-installation-state.dev.json for any other subscription. Discovery does not adopt resources whose names contain "jaws".

Full build / container preflight (developer / tester)

pwsh -NoProfile -File .\installer\Test-JawsPrerequisites.ps1 -RequireContainerBuild
Invoke-Pester .\tests\installer\ -Output Detailed
dotnet run --project tests/Jaws.FirstAgent.Tests

Expected: prerequisite checks succeed, Pester and .NET tests pass, and Docker reports Linux. These are developer/tester validation commands; do not interpret them as cloud deployment or Step C live acceptance. Consult the Developer/Tester Guide and full prerequisite specification for environment-specific troubleshooting.

2. Installation and acceptance by milestone

New subscription installation is not yet available. Step A discovery is available and read-only. The installer still has no approved provisioning command. Do not point Step C validation, or jaws-installation-state.dev.json, at a new subscription.

Expected new-customer install sequence (not yet executable)

  1. Choose your subscription, region, resource group and environment name.
  2. Run installer preflight: credentials, permissions, provider registration, quota, approved policies, networking and model availability.
  3. Review a complete cost-aware deployment plan, including resource names and role assignments.
  4. Approve provisioning; create the subscription-specific state file, models, agents, container registry, identity and tool integration infrastructure.
  5. Run all milestone validation gates; archive nonsecret acceptance evidence.

Existing deployment verification tools

Step A: Discover the selected subscription
.\installer\Install-Jaws.ps1 -Mode Discover -SubscriptionId <your-subscription-id> -NonInteractive

Expected: Outcome NoInstallationState. Azure Resource Graph rows for Foundry, Key Vault, and container registry resources are Unclaimed. AzureWrites is 0. The report is installer/.local/jaws-step-a-discovery.selected.generated.json. Reader must include Microsoft.ResourceGraph/resources/read. A denied query returns JAWS-AUTH-010 and names that action. This does not provision JAWS. Acceptance criteria: Step A.

Validate the report locally. This command does not call Azure:

.\installer\Test-JawsStepADiscovery.ps1 -ReportPath .\installer\.local\jaws-step-a-discovery.selected.generated.json

Expected: STEP-A PASS, Outcome NoInstallationState, and Azure writes: 0. JAWS-STEP-A-001 means the report is missing and is not a pass. JAWS-STEP-A-003 means a write or an adopted row. The same procedure is on the manual verification page.

To reconcile an existing state file instead:

.\installer\Install-Jaws.ps1 -Mode Discover -StateFile .\installer\config\jaws-installation-state.dev.json -NonInteractive

Expected: Outcome Reconciled when the named resources match Azure. The state file is not rewritten. Use this only for the subscription named in that file. Then run .\installer\Test-JawsStepADiscovery.ps1 -ReportPath .\installer\.local\jaws-step-a-discovery.dev.generated.json. STEP-A PASS requires Outcome Reconciled. JAWS-STEP-A-002 means drift.

Step B: Validate existing Foundry foundation

Step B was implemented for this DEV project, but its full first-time install is not a supported one-command Quick Start. Use the consolidated read-only through-Step-C validator below; it checks existing foundation dependencies without creating new resources. See Standard Guide.

Step C: Validate approved Supervisor → Investigation Planner integration
.\installer\Install-JawsThroughStepC.ps1 -Mode Validate

Expected: VALIDATED, no Azure configuration writes. Report: installer/.local/jaws-step-c-install.dev.generated.json.

Optional billable functional test:

.\installer\Install-JawsThroughStepC.ps1 -Mode Validate -AcknowledgeInferenceCharges

Expected: CLOSED, acceptance passed, TASK_STATE_COMPLETED. Report: installer/.local/jaws-step-c-final-acceptance.dev.generated.json.

Only if blocked on a documented, repairable gate:

.\installer\Install-JawsThroughStepC.ps1 -Mode Install -AcknowledgeStepCInstall

This may change Azure configuration. Review the repair gate list and obtain the necessary authorization first. It is not part of routine validation.

4. What successful installation must prove

A successful customer installation must demonstrate that the complete installed system operates in the customer's chosen subscription and permissions boundary, passes the applicable milestone tests, and produces auditable evidence. Current DEV acceptance proves only that one Supervisor can delegate to the A2A prompt planner and return a read-only plan; this is not sufficient for full product installation, VM investigation execution, MCP evidence collection, remediation or Teams operation.
