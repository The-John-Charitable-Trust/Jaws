1. Prepare for your first JAWS installation

This guide is for an organization installing JAWS in its own Azure subscription. You do not need an existing JAWS installation, a special development subscription, or a pre-created JAWS resource group. The installer is intended to collect your Azure subscription and deployment choices, assess prerequisites, present a deployment plan, obtain authorization and provision JAWS. Release status: Step B can provision an approved foundation. The complete first-time workflow, including Step C in a new subscription, is not yet implemented.

For detailed workstation configuration see System Prerequisites. For design and acceptance requirements see Implementation Roadmap and Microsoft References & Acceptance Criteria.

Hardware and operating system

  • Windows 11 workstation with hardware virtualization enabled. Development workstation recommendation: 32 GB RAM / 1 TB SSD, especially for Docker Desktop, WSL 2 and .NET builds. The repository does not establish an absolute minimum RAM/disk requirement.
  • Internet access to GitHub, Microsoft package downloads, Azure management endpoints, Microsoft Foundry and the authorized container registry.

Azure subscription, permissions, and readiness

Bring your own active Azure subscription. JAWS must not require a pre-existing JAWS deployment, a development subscription, or a fixed subscription ID. The intended installer workflow must ask the operator to select an accessible subscription and choose or create a target resource group. Current release limitation: Step B install creates the foundation only after an approved plan digest. A complete customer installation, including Step C, is still a release-blocking requirement.

PowerShell policy and source trust

Review Get-ExecutionPolicy -List before running downloaded PowerShell scripts. Respect MachinePolicy/UserPolicy; do not permanently bypass them. See Microsoft execution-policy guidance. Docker uses WSL 2 Linux containers, and hosted images target linux/amd64; Docker is not necessary for read-only inventory checks.

Get JAWS source and select the subscription

git clone --branch feature/step-c-investigation-publishing https://github.com/The-John-Charitable-Trust/Jaws.git
cd Jaws
az login
az account list --query "[].{Name:name,SubscriptionId:id,State:state}" --output table
# Choose your target Azure subscription:
az account set --subscription <your-subscription-id>
az account show --query "{name:name,id:id,tenantId:tenantId}" --output table
Get-ExecutionPolicy -List

Important: selecting any subscription above does not make the current Step C validation script a greenfield installer. The present Step A / Step C commands below depend on existing DEV state and are explicitly identified as existing-deployment verification only. For a new subscription, do not use the DEV state file or attempt to adopt unrelated resources. The forthcoming greenfield installer must obtain subscription/resource-group details interactively, verify RBAC/provider/quota requirements, request approval for billable provisioning, and create a distinct installation state.

2. Installation and acceptance by milestone

Step B can create a foundation after approval. Step C validation remains locked to the development project. Do not point the dev state file at a new subscription. A fresh-subscription Step B receipt has not been archived, so Step B is not accepted yet.

Work still ahead of a complete customer installation

  1. Choose your subscription, region, resource group and environment name.
  2. Run installer preflight: credentials, permissions, provider registration, quota, approved policies, networking and model availability.
  3. Review a complete cost-aware deployment plan, including resource names and role assignments.
  4. Approve provisioning; create the subscription-specific state file, models, agents, container registry, identity and tool integration infrastructure.
  5. Run all milestone validation gates; archive nonsecret acceptance evidence.

Existing deployment verification tools

Step A: Clone, authenticate, inventory, reconcile, verify

Step A is a read-only Azure discovery stage. A new customer may start with an empty subscription and must not supply the JAWS developer's installation state.

  1. Clone: In PowerShell 7, clone the reviewed GitHub branch to a local directory, enter the Jaws folder, and verify Test-Path .\\installer\\Install-Jaws.ps1 returns True.
  2. Authenticate: az login (on a machine without a browser, use az login --use-device-code), find your subscription with az account list --output table, select it using az account set --subscription <subscription-id>, confirm using az account show --output table.
  3. Inventory: Run az group list --output table and az resource list --output table. An empty result is valid.
  4. Reconcile (existing JAWS only): With your own verified JAWS state file, use the installer command below. Skip this operation for a new empty subscription.
  5. Review evidence: Confirm inventory and no Azure changes. For an existing JAWS deployment, review the three generated installer reports.
.\installer\Install-Jaws.ps1 -Mode Discover -EnvironmentName <environment> -StateFile "<your-existing-jaws-state.json>"

Expected results for completion

New customer: Identity/subscription confirmed, Azure resource inventory retrieved (possibly empty), no writes. Automated initialization of JAWS state is not yet available in installer v0.4.6. Existing JAWS: Accessible subscriptions scanned, target resources compared, reports generated under installer/.local/, gold-copy state unchanged, Azure writes: 0.

Acceptance criteria

  • A-00: Git clone verified in the local repository root.
  • A-01: Authorized subscription and tenant identified.
  • A-02: Readable resource scope inventoried; empty is valid.
  • A-03: Existing JAWS state and resources reconciled only when applicable.
  • A-04: Zero Azure configuration writes and no gold-state mutation.
  • A-05: Discovery/verification evidence retained.
  • A-06: Greenfield installer acceptance remains pending until automatic empty-subscription discovery and state initialization pass tests.

Step B: Plan, package, and install the foundation

Run Plan after az account set. Choose your own environment, resource group, and region. Do not use dev or rg-aiops-lab. Leave installer/config/jaws-stage-b-plan.example.json unchanged.

.\installer\Install-Jaws.ps1 -Mode Plan -NonInteractive -EnvironmentName your-environment -ResourceGroupName rg-jaws-your-environment -Location eastus
.\installer\Test-JawsStepB.ps1 -Mode Plan -ReportPath .\installer\.local\jaws-stage-b-plan.your-environment.offline.generated.json

Expected: STEP-B PLAN PASS, Subscription source: AzureCli, Install authorized: false, and a Plan SHA-256. Azure writes stay 0.

.\installer\Install-Jaws.ps1 -Mode Install -EnvironmentName your-environment -ResourceGroupName rg-jaws-your-environment -Location eastus -ApprovedPlanSha256 <plan-sha> -AcknowledgeStepBInstall
.\installer\Test-JawsStepB.ps1 -Mode Install

Expected: STEP-B INSTALL PASS, Foundry account jaws-foundry-your-environment, an image ending in @sha256:, and Agent status: active. Receipt: installer/.local/jaws-step-b-install.your-environment.generated.json. This creates billable resources and requires the .NET 10 SDK and Docker. Without -AcknowledgeStepBInstall the command stops at JAWS-STEP-B-010 and creates nothing. See the Step B walkthrough.

Step C: Validate approved Supervisor → Investigation Planner integration
.\installer\Install-JawsThroughStepC.ps1 -Mode Validate

Expected: VALIDATED, no Azure configuration writes. Report: installer/.local/jaws-step-c-install.dev.generated.json.

Optional billable functional test:

.\installer\Install-JawsThroughStepC.ps1 -Mode Validate -AcknowledgeInferenceCharges

Expected: CLOSED, acceptance passed, TASK_STATE_COMPLETED. Report: installer/.local/jaws-step-c-final-acceptance.dev.generated.json.

Only if blocked on a documented, repairable gate:

.\installer\Install-JawsThroughStepC.ps1 -Mode Install -AcknowledgeStepCInstall

This may change Azure configuration. Review the repair gate list and obtain the necessary authorization first. It is not part of routine validation.

4. What successful installation must prove

A successful customer installation must demonstrate that the complete installed system operates in the customer's chosen subscription and permissions boundary, passes the applicable milestone tests, and produces auditable evidence. Current DEV acceptance proves only that one Supervisor can delegate to the A2A prompt planner and return a read-only plan; this is not sufficient for full product installation, VM investigation execution, MCP evidence collection, remediation or Teams operation.
