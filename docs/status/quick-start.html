1. Prepare for your first JAWS installation

This guide is for an organization installing JAWS in its own Azure subscription. You do not need an existing JAWS installation, a special development subscription, or a pre-created JAWS resource group. The installer is intended to collect your Azure subscription and deployment choices, assess prerequisites, present a deployment plan, obtain authorization and provision JAWS. Release status, installer 0.4.10: Step A Discover reads an empty subscription and writes a receipt without creating resources. Step B provisioning code can create an approved foundation after a preflight report. Step C can validate the dev project, and it can read a Step B receipt when -EnvironmentName is set. Neither Step A nor Step B has a fresh-subscription acceptance receipt. A live Step C acceptance on a fresh subscription has not been recorded.

For detailed workstation configuration see System Prerequisites. For design and acceptance requirements see Implementation Roadmap and Microsoft References & Acceptance Criteria.

Hardware and operating system

  • Windows 11 workstation with hardware virtualization enabled. Development workstation recommendation: 32 GB RAM / 1 TB SSD, especially for Docker Desktop, WSL 2 and .NET builds. The repository does not establish an absolute minimum RAM/disk requirement.
  • Internet access to GitHub, Microsoft package downloads, Azure management endpoints, Microsoft Foundry and the authorized container registry.

Tester system requirements (Steps A and B)

Running the installer scripts needs less than a development build. No Docker Desktop, WSL, or .NET SDK is required. Step B Install builds the container image in Azure with az acr build, not on your machine.

  • OS: Windows 11 (21H2 or later)
  • RAM: 4 GB minimum, 8 GB recommended
  • Disk: 2 GB free (repo, Azure CLI, and local receipts)
  • Network: Outbound HTTPS to Azure and GitHub

Bring your own active Azure subscription. JAWS must not require a pre-existing JAWS deployment, a development subscription, or a fixed subscription ID. The intended installer workflow must ask the operator to select an accessible subscription and choose or create a target resource group. Current release limitation: Step B install creates the foundation only after an approved plan digest. A complete customer installation, including a live Step C acceptance, is still a release-blocking requirement.

2. Installation and acceptance by milestone

Console result. Each key milestone in Steps A–D prints four lines: Result: PASS or Result: FAIL, Ready for next step: true or false, Next step: the following command, and Evidence: the absolute path of the evidence file. Read that file for the pass or fail detail. When Azure returns an error the installer can name, the console also prints Issue and Action. A model rate limit names the Azure error and the two ways out: re-run Step B Install with -QuotaMode Dynamic, or wait for the limit to reset and retry. A Step B create that Azure refuses for lack of quota also prints Quota request with the application link. Ready for next step: false means stop. A PASS from a local stand-in is not a fresh-subscription receipt.
Step B acceptance re-reads Azure. Install-Jaws.ps1 -Mode Accept prints STEP-B ACCEPTANCE PASS only after the signed-in subscription shows the foundation and an active digest-pinned Supervisor. Step C for a new environment reads the Step B receipt through -EnvironmentName. A fresh-subscription acceptance has not been recorded, so Step B is not accepted yet and Step C on that environment is not accepted yet.

Work still ahead of a complete customer installation

  1. Choose your subscription, region, resource group and environment name.
  2. Run installer preflight: credentials, permissions, provider registration, quota, approved policies, networking and model availability.
  3. Review a complete cost-aware deployment plan, including resource names and role assignments.
  4. Approve provisioning; create the subscription-specific state file, models, agents, container registry, identity and tool integration infrastructure.
  5. Run all milestone validation gates; archive nonsecret acceptance evidence.

Expected results for completion

New customer: STEP-A DISCOVERY PASS, Discovery: Greenfield, Subscription source: AzureCli, State file required: false, State file written: false, Azure writes: 0, and Prepared for Step B: true. An empty subscription prints Resource groups: 0 and Resources: 0. The test script adds Live Azure read: false. Receipt: installer/.local/jaws-step-a-discovery.your-environment.generated.json. Acceptance criteria

  • A-00: Clone of main and the installer file are present.
  • A-01: The receipt names the signed-in subscription.
  • A-02: Resource counts are printed. Empty is valid.
  • A-03: Existing state is reconciled only when the state file exists.
  • A-04: Azure writes: 0 and no new file under installer/config/.
  • A-05: The discovery receipt is retained.
  • A-06: Greenfield Step A is not accepted until a real subscription prints STEP-A DISCOVERY PASS.
  • A-07, FedRAMP Moderate: Discovery creates no resource. Record any inventoried Foundry account, Key Vault, registry, storage account, or container app that is publicly reachable. An empty subscription has nothing to record. Step A does not authorize the subscription.

Without -AcknowledgeStepBInstall the command stops at JAWS-STEP-B-010 and creates nothing. -QuotaMode is Static or Dynamic and defaults to Static. Static leaves the gpt-5-mini deployment at GlobalStandard capacity 1. Dynamic creates it on the regional Standard SKU at capacity 1, because GlobalStandard rejects dynamicThrottlingEnabled. If a GlobalStandard deployment is already there, Dynamic Install deletes it and creates the Standard deployment, then sets the property. The plan digest stays the same. Extra tokens above capacity 1 are billed at the normal rate, and dynamic quota has no throughput ceiling. The console prints Quota mode: Static or Quota mode: Dynamic.

Step D writes the JSON catalog, one hosted virtual-machine specialist, and, outside the dev project, a private browser for the Supervisor and that specialist. The Investigation prompt planner does not receive the browser. Steps E (allow-listed Azure MCP investigation), F (deliberation skill and approval workflow), G (extensible observability MCP server), H (Teams conversation and project record), and I (end-to-end acceptance) are still planned. No installation or validation command exists for E–I. The design is in the implementation roadmap.

  • The Supervisor loads a versioned JSON catalog and routes only to specialists named there. The virtual-machine specialist is one hosted agent and owns one compute environment. A later specialist, such as network, storage, or ServiceNow change, is another catalog entry. A prompt specialist does not need a new container.
  • A tool is one callable action. A skill is a procedure the specialist loads for a matching task. Investigation and deliberation are skills. An approved change is a workflow that checks identity, RBAC, and human approval before one write tool runs.
  • The virtual-machine specialist calls an allow-list of Azure MCP tools for that machine: the machine and its identity, its network attachments, Azure Policy and Microsoft Defender evidence, and the metrics and logs for that machine. It does not receive the entire Azure MCP catalog.
  • Observability is one custom MCP server on that same compute environment. Each product action is a compiled module named by a JSON manifest. The manifest cannot add an arbitrary URL or a script. The first modules are Datadog, Azure Monitor, Microsoft Sentinel, and ServiceNow incident records.
  • A Teams conversation stores that thread. A project record stores the incident, decisions, approvals, and citations for every conversation in the project. Another project is not returned. Foundry long-term memory is reserved for one operator's preferences and is not the incident record.

See Step D in the acceptance register. The installer checks are not a fresh-subscription acceptance.

4. What successful installation must prove

A successful customer installation must demonstrate that the complete installed system operates in the customer's chosen subscription and permissions boundary, passes the applicable milestone tests, and produces auditable evidence. Each of Steps A–D also has a FedRAMP Moderate criterion for the resources that step creates. A functional pass on the public-egress account leaves that criterion open and leaves Customer installation accepted false. The FedRAMP configuration is a Foundry account created private, with specialists reached as private MCP or OpenAPI. Step B Install requests the ServiceNow login URL, username, and password, and the Datadog parameters, and stores supplied values in the Step B Key Vault. The generated install config lists every Azure resource and leaves FedRAMP Moderate false while any resource is public. The current default Datadog host is jaws-stepb-test. Install does not install the Datadog Agent or Step G. Set-JawsObservabilityIntegration.ps1 updates the same secrets later. Current DEV acceptance proves only that one Supervisor can delegate to the A2A prompt planner and return a read-only plan. Full product installation, VM investigation execution, MCP evidence collection, remediation, and Teams operation remain later steps.
