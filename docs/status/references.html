Step-by-step acceptance register

Step A: Azure Discovery and Reconciliation Dev reconciliation accepted; greenfield receipt not recorded

Value proposition: A first-time user establishes the authorized Azure subscription baseline without modifying infrastructure. If JAWS exists, the installer compares its verified state against deployed resources and produces reports. A clean subscription is a valid starting point.

Four activities: 1. Clone JAWS locally. 2. Authenticate and select subscription. 3. Inventory the accessible resource scope (empty permitted). 4. Reconcile only if there is an existing JAWS installation and valid state. 5. Verify evidence and zero Azure writes.

Expected results for completion: A new subscription prints STEP-A DISCOVERY PASS, Azure writes: 0, and State file written: false. An empty inventory is valid. Existing JAWS customers still receive the tenant scan and comparison, with unchanged state. Greenfield acceptance is not recorded.

Acceptance criteria
  • A-00: Git clone and repository root verified.
  • A-01: Authentication and selected Azure scope verified.
  • A-02: Readable resources inventoried and failures reported; empty is valid.
  • A-03: Existing JAWS deployments reconciled against their own state; new customers do not need one.
  • A-04: Zero Azure writes and unchanged authoritative state.
  • A-05: Evidence retained (inventory for new customers; installer reports for existing JAWS).
  • A-06: Greenfield automated discovery and state creation remain unaccepted until implemented and live-tested.

Microsoft sources: Azure CLI authentication, RBAC, Resource Graph, Azure Resource Manager.

Code: installer/Install-Jaws.ps1. Tests: tests/installer, manual cases. Tutorial: Step A walkthrough.

Verification state: Dev-project reconciliation remains the accepted Step A evidence. Greenfield Discover is implemented. Offline Pester passed against a CLI stand-in. A fresh-subscription discovery receipt has not been recorded, so greenfield Step A is not accepted.

Step B: Foundry foundation and packaging partial

Value proposition / achievement: An approved plan creates a Foundry account, project, model deployment, Key Vault, registry, project identity pull role, and a digest-pinned hosted Supervisor.

Deliverable: Install receipt installer/.local/jaws-step-b-install.<environment>.generated.json with hosted Supervisor version 1 active. A fresh-subscription receipt has not been recorded.

Microsoft technical source: Deploy a hosted agent (source supports implementation guidance; it does not independently certify JAWS acceptance).

Implementation: installer/Install-Jaws.ps1 and src/Jaws.Supervisor.Host.

Tests: installer/Test-JawsStepB.ps1.

Acceptance criteria:
  • B-00: Plan prints STEP-B PLAN PASS with the Azure CLI subscription and Azure writes: 0
  • B-01: jaws-stage-b-plan.example.json keeps the placeholder subscription
  • B-02: Package prints STEP-B PACKAGE PASS and Status: LOCAL_PACKAGE_CREATED
  • B-03: Registry push: false and Foundry deployment: false
  • B-04: Jaws.Supervisor.Host.dll is present under installer/.local/supervisor/publish
  • B-05: Install without -AcknowledgeStepBInstall stops at JAWS-STEP-B-010 and performs no Azure writes
  • B-06: Approved install prints STEP-B INSTALL PASS, with hosted Supervisor version 1 active and an image pinned to @sha256:
  • B-07: The dev environment, rg-aiops-lab, and jaws-installation-state.dev.json stay unchanged
  • B-08: Install-Jaws.ps1 -Mode Accept prints STEP-B ACCEPTANCE PASS, Live Azure read: true, and Azure writes: 0 after re-reading the account, project identity, Succeeded deployment, Key Vault RBAC and purge protection, registry admin disabled, AcrPull, and hosted Supervisor version 1 active on the receipt digest

Verification state: Preflight and Accept are implemented. Offline Pester passed against a CLI stand-in. A fresh-subscription receipt has not been recorded, so provisioning, functional acceptance, and customer installation are not accepted. The plan digest does not authorize an unbounded cost.

Step D: VM specialist + compute partial

Value proposition / achievement: The installer can write one JSON catalog and one hosted virtual-machine specialist. A fresh-subscription receipt has not been recorded, and the Supervisor image does not yet load the catalog.

Deliverable: installer/Install-JawsStepD.ps1 with Validate, Install, and Accept. Evidence files are installer/.local/jaws-step-d-validate.<environment>.generated.json, jaws-step-d-install.<environment>.generated.json, jaws-step-d-acceptance.<environment>.generated.json, and jaws-specialist-catalog.<environment>.generated.json.

Microsoft technical source: Hosted agents and Foundry agents REST (sources support implementation guidance; they do not independently certify JAWS acceptance).

Implementation: installer/Install-JawsStepD.ps1.

Tests: tests/installer/StepDInstall.Tests.ps1 with a CLI stand-in. A stand-in pass is not a live receipt.

Acceptance criteria:
  • The console prints Result: PASS or Result: FAIL, Ready for next step, Next step, and the absolute Evidence path
  • Validate is read-only and requires a Step C acceptance file with PASS and TASK_STATE_COMPLETED
  • Install without -AcknowledgeStepDInstall fails as JAWS-STEP-D-001 and creates no specialist
  • One hosted specialist, id virtual-machine, owns the only compute environment
  • An unknown tool, a phase id, a second compute environment, or vm.run-command without approve-vm-change is refused
  • A prompt specialist may share that compute id; it does not require a new Supervisor image
  • Outside dev, the specialist image is the Step B digest and a second Install does not post again
  • The dev project binds jaws-investigation-dev and does not post a second agent
  • Supervisor version inventory and the dev installation state stay unchanged
  • Accept re-reads Azure, keeps Customer installation accepted: false, and prints Ready for next step: false because Step E is not installable

Verification state: Offline tests cover the checks above. Runtime Supervisor routing, Azure MCP invocation, and a fresh-subscription receipt are not recorded. Step D is not accepted.

Review standards

Before promoting a milestone: record a deployment/version digest if applicable, its test commands and actual output, relevant Microsoft SDK/API version, the accepted evidence, open defects, and a signed-off value statement. Planned acceptance checks are requirements, not passed test results.
