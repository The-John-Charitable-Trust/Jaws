JAWS Agent Framework Tutorial

Introduction

JAWS is a step-by-step reference implementation for building a governed, full-stack agentic operations platform with the Microsoft Agent Framework.

Modern operations teams are being asked to manage increasingly complex cloud environments while also responding faster, proving compliance, reducing manual toil, and coordinating work across multiple enterprise systems. The challenge is not simply adding AI to operations. The harder problem is building a full-stack agentic platform that can reason over live cloud context, call approved tools, respect security boundaries, preserve operational evidence, and guide users through real workflows such as creating observability coverage, validating webhook delivery, and opening an IT service management incident.

JAWS uses the Microsoft Agent Framework tutorial as scaffolding for a real operational scenario. Rather than treating the Microsoft tutorial as a set of isolated code samples, this tutorial incrementally builds an agentic operations platform that can inspect Azure resources, recommend Datadog monitors or synthetic tests, use a hardened custom MCP server, validate alert delivery through an approved webhook contract, and create a ServiceNow incident with evidence and operational reasoning.

The goal is to show how each Microsoft Agent Framework concept becomes part of a working enterprise architecture. Step 1 begins with the first agent. Step 2 adds tools. Step 3 introduces multi-turn conversation state. Step 4 adds memory and external knowledge. Later steps extend the same platform into workflows, hosting, deployment, and operational governance. Each section explains the concept, shows the implementation, updates the installer where needed, and defines test cases with expected results.

The value to the reader is practical and cumulative. By following the tutorial, you are not only learning how to call an LLM from C#. You are learning how to assemble agents, tools, MCP boundaries, memory, SaaS integrations, Azure deployment assets, and verification tests into a platform that can be deployed into your own Azure environment. The tutorial is designed for architects, developers, and platform engineers who need to understand both the code and the operational decisions behind it.

This approach is unique because it treats the Microsoft Agent Framework documentation as a product-building path rather than a collection of disconnected examples. Each release of JAWS corresponds to a step in the Microsoft documentation, so the reader can see exactly how the platform evolves from a minimal first agent into a governed, testable, multi-system agentic operations platform.

Source code and releases The full step-by-step source code is available on GitHub at https://github.com/cezjah/jaws. Each release is aligned to the corresponding Microsoft Agent Framework tutorial step, making it possible to inspect the code, run the tests, deploy the platform, and compare each implementation phase against the documented concepts.

System Requirements

Before installing JAWS, prepare the required accounts, tools, permissions, and configuration values. The installer can deploy and configure the JAWS platform, but it does not create the customer's SaaS accounts, Azure subscription, GitHub account, Teams license, or model quota.

Required Accounts

  • Azure subscription for the JAWS deployment.
  • Azure AI Foundry or Azure OpenAI access with an existing model deployment.
  • Datadog trial, evaluation, or licensed account.
  • ServiceNow developer instance or licensed instance.
  • GitHub account with access to the JAWS repository.
  • Microsoft Teams license if Teams integration is enabled.

Required Local Tools

  • Git
  • PowerShell 7 or later
  • Azure CLI
  • .NET 10 SDK
  • Visual Studio Code

Optional developer tools include OpenAI Codex, Claude Code by Anthropic, and GitHub Copilot. The Step 1 code in this tutorial targets net10.0.

Azure Permissions

For the simplest evaluation, use a dedicated Azure subscription and sign in with an account that has Owner on that subscription. This lets the installer deploy resources, assign managed identity permissions, and apply optional Azure Policy compliance settings without interruption.

If your organization requires least-privilege access, use the minimum role for the installation mode:

Installation ModeRequired Azure Permission
Basic resource deploymentContributor on the target subscription or resource group
Managed identity role assignmentsUser Access Administrator plus Contributor, or Owner
Azure Policy compliance profilePermission to create policy assignments at the selected scope
Full evaluation in a new subscriptionOwner on the subscription

The installer creates and configures Azure resources such as App Service, managed identity, Key Vault, Log Analytics, Application Insights, storage, RBAC assignments, and optional Azure Policy assignments.

Required Azure Configuration

  • Subscription ID and tenant ID.
  • Target Azure region.
  • Resource group name or permission to create one.
  • Azure AI Foundry or Azure OpenAI endpoint.
  • Model deployment name.
  • Approved authentication method, preferably managed identity for deployed workloads.

Datadog Requirements

During installation, provide the Datadog site URL and an admin username and password, or credentials with equivalent permissions. The account must be able to create and manage monitors, synthetic tests, webhooks, API/application keys, tags, and integration settings.

Optional Datadog Agent testing requires an Azure-hosted VM. Recommended demo minimum: Ubuntu 22.04 LTS or Windows Server 2022, 2 vCPU, 4 GB RAM, 30 GB disk, and outbound HTTPS access to Datadog.

ServiceNow Requirements

During installation, provide the ServiceNow instance URL and an admin username and password, or credentials with equivalent permissions. The account must be able to create and update incidents, read CMDB records, create demo CMDB records when selected, and configure the required integration user or authentication settings.

Compliance Options

During installation, select one compliance profile: None, FedRAMPModerate, CMMC20L2, or NIST80053R5.

When a compliance profile is selected, the installer uses the selected profile to configure supported Azure resources with matching baseline settings, such as HTTPS-only endpoints, TLS 1.2 or higher, managed identity, Key Vault-backed secrets, diagnostic settings, application logging, audit logging, least-privilege RBAC, and the corresponding Azure Policy initiative assignment where available.

Compliance note JAWS can deploy resources using compliance-aligned Azure configurations and assign Azure Policy initiatives. It does not certify the deployment as compliant. Final compliance depends on the customer's environment, operations, evidence, remediation, governance, and audit process.

Network And Security Requirements

  • Outbound HTTPS from JAWS to Azure, Datadog, ServiceNow, GitHub, and Microsoft identity endpoints.
  • Public HTTPS endpoint for Datadog webhooks if webhook validation is enabled.
  • Public HTTPS endpoint for Teams callbacks if Teams integration is enabled.
  • Secrets stored in Azure Key Vault or Key Vault-backed app settings.
  • No SaaS API keys or credentials stored in source code.

Installation Overview

The installer deploys a working JAWS evaluation environment into the selected Azure subscription and configures the supporting SaaS integrations when valid credentials are supplied. After installation, the user has a hosted agentic AI platform that can receive natural-language requests, call approved tools through a custom MCP server, retrieve operational context, and execute governed workflows.

Azure Resources

The Azure deployment includes the resource group, App Service Plan, JAWS API App Service, managed identity, Key Vault, Log Analytics workspace, Application Insights, storage account, app settings, Key Vault references, RBAC assignments, and optional Azure Policy assignments.

Naming And Governance

The installer applies the naming inputs selected during setup to generate governed resource names. For globally unique resources, the installer checks availability and selects the nearest compliant variation when the preferred name is unavailable. Final names, selected region, tags, compliance profile, and deployed resource IDs are written to the installation manifest.

Regulatory Compliance

If a compliance profile is selected, the installer deploys supported Azure resources with compliance-aligned settings and assigns the matching Azure Policy initiative where available. Supported evaluation profiles include FedRAMPModerate, CMMC20L2, and NIST80053R5. JAWS aligns deployment settings and evidence collection; it does not certify compliance.

Secrets And Credentials

Secrets such as Datadog credentials, ServiceNow credentials, API keys, webhook secrets, model credentials, and Teams configuration values are stored in Azure Key Vault or referenced through Key Vault-backed app settings. Secrets are not stored in source code or plain-text tutorial files.

RAG And Operational Context

The installation includes a starter knowledge store for retrieval-augmented generation. The content is organized into practical categories:

  • Curated context: approved runbooks, Datadog monitor guidance, webhook contracts, ServiceNow incident rules, compliance mappings, and agent operating instructions.
  • Simulated context: demo Azure inventory, sample ServiceNow CMDB records, sample incidents, and testable observability scenarios.
  • Live context: authorized Azure inventory, Azure Policy state, Azure Monitor evidence, Datadog monitor status, and ServiceNow incident or CMDB lookups collected through approved tools.
  • Generated evidence: workflow results, test outcomes, tool call summaries, approval references, and incident evidence created during JAWS operation.

For the evaluation install, curated and simulated context is stored in the configured JAWS knowledge store, such as Azure Blob Storage. Later tutorial steps add provider options for Azure AI Search, SharePoint via Microsoft Graph, and AI Foundry knowledge sources.

SaaS Integration Setup

For Datadog, the installer validates connectivity and can configure approved webhook, monitor, synthetic test, and tagging assets. For ServiceNow, the installer validates connectivity and configures the incident and CMDB integration contract. For Teams, the installer prepares the Teams app manifest package as a ZIP file for upload to the Teams admin center or for approved sideloading, depending on the tenant policy. Teams integration requires a valid Teams license plus the required Microsoft identity and bot configuration permissions.

Installation Outcome

At the end of installation, the user can open the JAWS endpoint, verify health, confirm secure configuration, test the custom MCP server, query curated and simulated knowledge, validate SaaS connectivity, upload or sideload the generated Teams app manifest ZIP, and use the Teams app to run the main scenario: investigate an Azure resource, deliberate over Datadog coverage, approve deployment, create the Datadog monitor or synthetic test, validate the webhook path, and confirm the ServiceNow incident.

Concept of Operations

JAWS is an agentic operations platform that lets a user chat in Microsoft Teams, investigate an operational need, deliberate with specialized agents, approve a governed action, and deploy an evidence-backed change across Azure, Datadog, and ServiceNow.

Main Use Case

The main tutorial use case starts in the Teams app. A user asks JAWS which Azure resources need Datadog monitors or synthetic tests. JAWS investigates the authorized Azure environment, retrieves curated observability guidance, evaluates the resource candidates, and explains its recommendation. The user then selects a resource, asks JAWS to proceed, supplies or confirms an approval reference, and JAWS deploys the Datadog monitor or synthetic test, configures the approved webhook path, validates the notification flow, and creates or updates the ServiceNow incident.

Conversation Flow

The expected Teams conversation has four phases. First, JAWS investigates and explains which resources need coverage. Second, JAWS deliberates with the relevant support, governance, and deploy agents to decide what should be created and what approval is required. Third, JAWS pauses at a human-in-the-loop approval checkpoint before any write-capable action. Fourth, after approval, JAWS performs the deployment through tool calls behind the custom MCP boundary and validates the result by confirming the Datadog asset, webhook delivery, and ServiceNow incident evidence.

External Systems

JAWS coordinates across external SaaS and cloud platforms that are owned, operated, licensed, and governed by their respective vendors. Microsoft Azure is Microsoft's cloud platform for hosting applications, infrastructure, identity, monitoring, policy, and security services. Datadog is a third-party SaaS observability platform from Datadog, Inc. for metrics, logs, traces, synthetic tests, monitors, alerts, and webhook notifications. ServiceNow is a third-party SaaS IT service management platform from ServiceNow, Inc. for incidents, configuration management, change workflows, approvals, ownership records, and operational history.

JAWS does not replace these systems. It coordinates approved actions across them, applies customer-defined governance rules, and records evidence so the user can understand what was observed, what was changed, which vendor system was used, and why.

Agentic AI Responsibilities

The first JAWS release path uses a small set of role-oriented agents. The support agent explains findings and operational impact. The governance agent evaluates policy, approval, and compliance context. The deploy agent performs approved changes. The workflow agent coordinates multi-step execution and validation. Each agent receives only the tools and permissions required for its role, and each response should make clear whether JAWS is recommending, planning, executing, or validating.

Tool And MCP Boundary

JAWS uses a custom MCP server as the controlled tool boundary. The MCP server exposes approved tools for Azure inventory, Datadog, webhook validation, ServiceNow, policy evidence, and operational knowledge. It is hardened so tool calls are authenticated, authorized, logged, schema-validated, and constrained by customer configuration. Write-capable tools require explicit approval before execution.

Approval And Evidence Flow

JAWS separates recommendation from execution. A user can ask for recommendations without changing anything. When a requested action would create or modify Datadog, ServiceNow, Azure, or other external assets, JAWS uses a human-in-the-loop workflow checkpoint and requires an approval reference before execution. After execution, JAWS returns an evidence summary showing the requested action, tool calls performed, resources affected, generated links, webhook validation result, ServiceNow incident result, and final pass/fail status.

Definition Of Done

The scenario is complete when the user can verify the Datadog monitor or synthetic test in Datadog, see the approved webhook configuration, trigger or observe a Datadog notification, confirm JAWS received the event, and inspect the ServiceNow incident that includes operational reasoning, evidence, affected resource context, and the workflow test result.

Installation

The installation instructions grow with each release. Release 0.1 corresponds to Microsoft Agent Framework Step 1 and installs only the minimum Azure-hosted JAWS agent surface required to prove model connectivity and agent execution.

Step 1 Installation

For Step 1, deploy JAWS into a new Azure resource group using a generated bootstrap file. The repository includes only an example bootstrap JSON file. Each user creates a local bootstrap file during installation so tenant-specific values, names, endpoints, and secrets are not committed to GitHub.

The Step 1 installer will collect or generate the resource naming inputs, Azure subscription and region, Azure AI Foundry or Azure OpenAI endpoint, model deployment name, and deployment target settings. It will deploy the minimum hosted API, configure managed identity where supported, store sensitive values in Key Vault or Key Vault-backed app settings, and write the final selected resource names to the local installation manifest.

Step 1 Success Test

Step 1 is successful when the deployed JAWS endpoint reports healthy configuration, the first agent can call the configured model, and a test request returns a concise answer from the Step 1 agent. The test evidence should include the API health result, agent run result, deployment manifest location, and the release version 0.1.

Step 1: Your First Agent

Release 0.1 implements the first JAWS agent in alignment with Microsoft Agent Framework Step 1. The goal is intentionally narrow: create a minimal, well-documented agent that can receive a request, call the configured model, and return a response from the deployed JAWS API.

Code Deliverables

The Step 1 code must be documented with comments that explain what the code is doing and how it maps to Microsoft Agent Framework Step 1. Comments should clarify the agent construction, model configuration, credential usage, request handling, and the call that executes the agent. Comments should explain intent, not restate obvious syntax.

The initial source layout should separate the hosted API, agent implementation, configuration model, installer assets, and tests. A suggested layout is:

PathPurpose
src/Jaws.ApiHosted API surface for the JAWS tutorial platform.

Configuration Deliverables

Step 1 uses an example bootstrap JSON file in source control and a generated local bootstrap file during installation. The example file documents the required properties without containing real tenant values, SaaS credentials, API keys, or secrets.

The local bootstrap file will include values such as subscription ID, tenant ID, Azure region, naming inputs, Azure AI endpoint, model deployment name, and selected deployment mode. Secrets are stored in Key Vault or Key Vault-backed application settings rather than in the bootstrap JSON.

Test Deliverables

Every release must include tests in the GitHub repository. For release 0.1, tests should prove configuration validation, naming-policy output, bootstrap parsing, API health behavior, and successful first-agent execution. Where live Azure or model access is required, tests should clearly separate local unit tests from live deployment validation.

Release Rule

Each minor release maps to one Microsoft documentation step. Release 0.1 maps to Step 1. Release 0.2 maps to Step 2. This keeps code, docs, installer behavior, and tests aligned with the tutorial progression.

Create the first JAWS agent. The comments call out how the code maps to Microsoft Agent Framework Step 1:

C#
using System;
using Azure.AI.Projects;
using Azure.Identity;
using Microsoft.Agents.AI;

// Step 1 creates the first minimal agent. It does not add tools, memory, or workflows yet.
var endpoint = Environment.GetEnvironmentVariable("JAWS_AGENT_ENDPOINT")
    ?? throw new InvalidOperationException("Set JAWS_AGENT_ENDPOINT.");

var deploymentName = Environment.GetEnvironmentVariable("JAWS_AGENT_DEPLOYMENT_NAME")
    ?? throw new InvalidOperationException("Set JAWS_AGENT_DEPLOYMENT_NAME.");

// DefaultAzureCredential lets local developers use Azure CLI login and deployed apps use managed identity.
var credential = new DefaultAzureCredential();

// AIProjectClient connects to the Azure AI Foundry project or Azure OpenAI-compatible project endpoint.
// AsAIAgent creates the Agent Framework agent used by Step 1.
AIAgent agent = new AIProjectClient(new Uri(endpoint), credential)
    .AsAIAgent(
        model: deploymentName,
        name: "JawsStep1Agent",
        instructions: "You are JAWS, a concise agentic operations assistant. For Step 1, answer without tools.");

// RunAsync is the Step 1 execution point: send one request and return the model response.
AgentRunResponse response = await agent.RunAsync("Explain what JAWS Step 1 proves.");

Console.WriteLine(response.Text);

The same Step 1 idea in Python creates an agent and calls run. This tutorial shows Python for comparison only; the implemented JAWS reference path is C#.

Python
from azure.identity.aio import AzureCliCredential
from agent_framework import Agent
from agent_framework.azure import FoundryChatClient

# Step 1 creates a single agent and sends one message.
# JAWS implements this fully in C#, but the Python shape mirrors the Microsoft tutorial.
client = FoundryChatClient(
    project_endpoint="https://example-project.services.ai.azure.com/api/projects/example-project",
    model="gpt-4.1-mini",
    credential=AzureCliCredential(),
)

agent = Agent(
    client=client,
    name="JawsStep1Agent",
    instructions="You are JAWS. For Step 1, answer without tools.",
)

result = await agent.run("Explain what JAWS Step 1 proves.")
print(result)

Expose the first agent through a small API endpoint so the deployed environment can be tested:

C# Minimal API
app.MapPost("/api/agent/step1/run", async (Step1Request request, Step1Agent agent) =>
{
